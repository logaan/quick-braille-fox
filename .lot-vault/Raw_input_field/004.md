Done — the drill input is now a plain, uncontrolled text field that VoiceOver
fully owns, exactly as you sketched.

## What was actually wrong
The input was already a real `<input>`, but it was a *controlled* React field
(`value: vm.typed`) and the store rewrote that value on the fly via
`stripUnexpectedTrailingSpaces`. Writing the field's value back in the middle
of a VoiceOver word commit desynced VoiceOver's braille-screen-input word
buffer from the DOM — that's why a "finished" word got modified and a mistake
became impossible to back out of.

## The change
- The field is now uncontrolled: we only ever *read* it and compare against
  the prompt; nothing writes its value mid-prompt. It clears only by
  remounting (keyed on a store-owned prompt epoch) at a real prompt change.
- Trailing-space tolerance moved into `normalizeTypedValue`, a read-only
  comparison step that also drops a stray leading space and collapses
  VoiceOver's doubled spaces — none of which ever touches the field.
- The input stays visually hidden, so a space-noisy raw value is never seen;
  the visible monkeytype colouring follows the normalised comparison.

## Verification
- Full suite green: 102 tests (added 4 — leading-space recovery, doubled-space
  collapse, and the per-prompt remount key; existing trailing-space + qbf
  behaviour unchanged).
- Drove the real app in headless Chrome over CDP: normal typing still
  completes and advances; a stray leading space leaves the field holding " "
  yet reads as nothing typed; typing on top of it (field = " d") still matches
  "d" and recovers — proving we no longer fight what VoiceOver produced.
