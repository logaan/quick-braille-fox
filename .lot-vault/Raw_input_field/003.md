Diagnosis + plan for the raw input field.

## Root cause
The drill input is already a real `<input type="text">`, but it is a
**controlled** React field: `value: vm.typed`, where `vm.typed` mirrors the
core model. The store's `stripUnexpectedTrailingSpaces` sometimes feeds
`keystroke` a value different from what's in the DOM field (stripping
VoiceOver's spaces), so React then rewrites the DOM field's `.value` back to
the model's version. That mid-composition write-back desyncs VoiceOver's
braille-screen-input word buffer from the DOM — which is why a word we
"consider completely typed" gets modified and a mistake becomes unrecoverable.

## Fix (matches your note)
Let the field be a plain, uncontrolled text box that VoiceOver fully owns; we
only ever *read* it and compare against the target — never write back
mid-prompt.

1. drill.ts: drop `value: vm.typed`, use `defaultValue: ''` plus a per-prompt
   `key` so the field is uncontrolled and only clears (remounts) at a genuine
   prompt change, never mid-typing.
2. store/view: add a store-local `promptKey` (epoch bumped on advance/reset)
   for that remount key. No core changes.
3. store: replace the write-back `stripUnexpectedTrailingSpaces` with a pure
   `normalizeTypedValue` used only for comparison + qbf cell counting — drops
   a stray leading space, collapses VoiceOver's doubled spaces, and tolerates
   the trailing space at word/sentence commit. The uncontrolled field means
   this normalization never rewrites what VoiceOver sees.

The input stays visually hidden, so the (possibly space-noisy) raw field is
never seen; the visible monkeytype colouring is driven by the normalized
`vm.typed` as before. Existing trailing-space + qbf tests should still pass;
I'll add coverage for leading/doubled-space recovery.
